# 把一座岩馆装进手机

抱石的人都听过一句话：这条线是给高个子定的。

同一条线，188 的人伸手就到的点，152 的人要多踩三脚，或者干脆跳。别人的走法（圈里叫 beta）抄不了，因为身体不一样。我想做一个东西来回答这个问题：**换一副身体，这条线该怎么爬？**

要回答它，得先有两样东西：一面量得准的墙，和一个会爬墙的模型。这篇手记写的是这两样东西怎么来的。成品是一个叫 BetaBuddy 的 App，文末有下载。

先说素材。我没有激光扫描仪，也没有馆方的图纸，手里只有手机拍的攀爬视频。这些视频只当测量参考用，本文和 App 里的画面全部是自己建的模型，没有任何原始影像。

**第一个发现：墙上自带一把尺子。**

从视频里量尺寸，最头疼的是没有参照物。直到我注意到岩壁上那些密密麻麻的小黑点：装岩点用的螺母孔。它们是工厂按固定间距打的，横向 25 厘米，相邻两排错开 12.5 厘米。

这就是一块铺满整面墙的标定板。

::: diagram bb-lattice

做法很朴素：在一帧画面里把孔找出来，认出它们属于同一套点阵，再拟合一个单应矩阵，把像素坐标换成墙面上的米。一面墙认出 111 个孔，残差 2.8 毫米。

后来我拿另一个机位拍的同一面墙单独再标一次，比较同一批特征点换算出来的位置：平面上 7 个点平均差 1.1 厘米。更有意思的是，两次标定各自选的坐标原点差了 (−0.50, +0.24) 米，正好是孔距的整数倍。两次认到的是同一套孔，只是各自从不同的孔开始数。

这把尺子也有坑。点阵是周期性的，算法很容易“错一格”：整面墙平移 12.5 厘米，所有孔照样对得整整齐齐。稠密立体匹配在光墙上被这种周期纹理骗得很惨，最后只有和稀疏点一致的那部分结果被留下来。

**第二个发现：把人去掉，比想象中容易。**

墙的贴图不能带着人。好在示范视频大多是固定机位：手机架在地上，人在画面里爬来爬去，墙不动。把很多帧合成一张，动的东西就被挤掉了，剩下一张干净的墙。

三十多个固定机位各出一张干净底图，这些底图本身又可以当作多视角照片，丢进三维重建里解出每个机位的位姿。

**第三个发现：我以为的坡度是错的。**

一开始我凭感觉给两面墙写了 −12° 和 −10° 的倾角，觉得它们是缓坡。三维重建跑完，实测是 +0.8°，几乎竖直。其中一条线顶部那块板更离谱：我把它当成和主墙共面，推出结束点高 4.68 米；实测那块板外倾 44°，结束点其实在 4.0 米高、离主墙面 0.9 米的地方。

重力方向是这么估的：人拿手机拍视频时，画面的水平边大体是水平的。把所有帧的水平轴放在一起，它们张成一个平面，这个平面的法线就是重力。机位转动范围越大，估得越准。转了 75° 的那段，重复抽样的标准差是 0.2°；只转了 37° 的那段，我只敢说 ±3°。

还有一个教训：别把整段视频一次性丢进去重建。不同的墙长得太像了，同样的灰板、同样的孔，算法会把两面墙的画面粘成一面。最后是一面一面单独建，再靠相邻两面共享的墙板把它们拼起来。

整座馆建下来是五组岩壁加两块训练板。每面墙内部准到厘米级；各面在馆里的绝对位置靠平面图和柱子对齐，只有 ±1 米左右。对爬线来说够了，因为一条线只在一面墙上。

**第四个发现：自动分割岩点不靠谱，得一个一个看。**

按颜色自动分割出来的岩点，漏的漏，错的错。黑色、灰色、白色的点和墙面分不开，大造型经常被切成几块。

最后的办法很笨：把拉正的墙面切成带坐标网格的小片，每个岩点给一个框，框里再自动抠轮廓，画回去核对。标一轮，换一个人复查一轮，然后随机抽样。第二次抽样看了 672 个条目：漏标 0，误标 8 个，1.2%，全是相邻两块板的接缝处同一个点被标了两次。

线路也是逐条确认的：哪个是起步点，哪个是结束点，中间用了哪些点。规则只有一条，一条线只用同一种颜色的岩点，手脚都算。示范的人偶尔会踩到别的颜色上，那是踩错了，不算。一共 72 条。

**现在墙有了。怎么让模型知道一个点该怎么抓？**

墙上的岩点在数据里只是一圈轮廓加一个凸出高度。但爬的人看一眼就知道：这是个月牙，要从凹的那边扣；那是根竖条，得侧着拉。

这部分我没用任何学习模型，就是几何。

::: diagram bb-hold

对轮廓做一次主成分分析，得到长轴方向和长宽比。再算凸包，用轮廓面积除以凸包面积得到实心度。缺掉的那块（凸包减去轮廓）有自己的重心，从它指向岩点重心的方向，就是手该用力的方向：

```python
solid = area / hull_area
if solid < 0.86:                       # 缺了一块：月牙
    notch = (hull_area * hull_c - area * c) / (hull_area - area)
    pull = normalize(c - notch)        # 从开口指向有肉的一侧
elif aspect >= 2.0:                    # 长条：受力垂直于长轴
    pull = normal_of(long_axis)        # 接近竖直的长条 → 侧拉
```

受力方向决定了身体得在哪一侧。一个侧拉点，肩膀必须在它的另一边才吃得上力；一个反提点，人得先爬到和它差不多高。有了这条约束，模型才会侧身、换脚、先上脚再出手，而不是面朝墙一路硬拉上去。

**然后是爬。我把它做成了一个最短路问题。**

::: diagram bb-search

状态很小：左手、右手、左脚、右脚各在哪个点上。每一步只动一只手或一只脚。从“双手在起步点、双脚在地上”出发，找到“双手在结束点”的代价最小的路径，用的是加权 A*。

难的是每条边的代价。四肢的位置定了，身体怎么摆还有无数种可能。所以对每个状态，先在“骨盆位置 × 躯干倾角”的网格上搜一遍，找最省力的姿态：重心落在脚的支撑范围外面多少，手就得扛多少；扛的这部分除以“岩点好抓程度 × 力量体重比”，就是这一刻有多费劲。移动一只手的时候，那只手不受力，剩下三个点得撑得住，这是一步里最难的瞬间。

选出来的姿态还要过一道验证：一副三维骨架，肢段长度按身高取人体测量学比例，肘和膝只能往一个方向弯，肩和髋的活动范围跟着柔韧走，任何关节不能穿进墙里。过不了就换下一个候选姿态，全都过不了，这个状态就不存在。App 里你看到的小人，画的就是这同一副骨架解出来的结果，所以“算的”和“画的”不会对不上。

身材参数是这么接进去的：

```js
ratio  = (30 + 7 * strength) / weight   // 上肢力量 ÷ 体重：手点能扛多少
legfac = weight / (45 + 4 * power)      // 腿的负担，也决定能跳多远
hipAbd = (35 + 50 * flex) * RAD         // 髋能开多大：脚能抬多高
arm    = (height + ape - shoulder) / 2  // 臂展：够不够得着
```

六个滑块：身高、体重、臂展差、力量、爆发、柔韧。它们不直接改答案，只改图里有哪些边、每条边多贵。

::: diagram bb-compare

这是我最喜欢的一个例子。同一条线，高瘦长臂的 7 步走完；152 厘米、柔韧很好的那位走了 18 步，中间挂了一次脚跟。没有人告诉模型“矮个子要多踩几脚”，这是最短路自己算出来的。

够不着的时候可以跳。起跳能多够多远，由爆发、体重和脚点好坏决定；抓住之后双脚悬空，那个手点必须够好才挂得住，然后再把脚找回来。

::: diagram bb-dyno

脚跟挂和脚尖勾也加了，但只在别的办法都不行、或者有一步特别难的时候才启用。不然模型会满墙挂脚，像只树懒。

**它算得对吗？**

::: diagram bb-scores

每条线都有真人示范，我把示范的走法记下来当参照，再用示范者的身材去算。70 条里 43 条基本一致，23 条部分一致，4 条无解。

该说的不足：

- 挂脚和勾脚基本没复现。示范里用到的 8 条线，模型只在 1 条上选了同一只脚、同一个点。
- 岩点好不好抓是从形状猜的，没有摩擦系数，也不分指力。
- 个别动作的中间帧，膝盖或手肘会擦进墙面十几厘米。
- 难度排序在两面墙上很弱：模型觉得难的线，不一定是定线员觉得难的线。
- 岩点的凸出高度，多视角拍到的是实测，只有单机位的是按外形估的。

所以 App 一进岩馆就写着：这是模型的推演，不是教练建议。它适合回答“有没有另一种走法”，不适合回答“我能不能过”。

**最后，装进手机。**

整座馆打成一个包：模型、72 条线、预先算好的 8 种身材的解、求解器本身，加上一个三维页面，一共 11 MB。包里没有照片贴图，墙是纯色的，岩点按真实轮廓和颜色建模。

App 是一层很薄的原生壳：iOS 用 SwiftUI，Android 用 Kotlin 和 Compose。壳和包之间只有一份很短的约定：壳告诉页面打开哪面墙、哪条线、用什么语言；页面告诉壳“我好了”“用户选了这条线”。两个平台装的是同一个包，一个字节都不用改。

预设身材的解是提前算好的，点开就播。自己拖滑块调出来的身材，求解器在手机上的后台线程里现算，最长十秒左右。

岩馆这部分不联网。iOS 上页面走自定义协议从安装包里加载，其它请求一律拦掉；Android 版干脆没有申请网络权限。整座馆和你的攀爬记录都只在手机里。

顺便记一个好笑的坑。Android 模拟器上，姿态识别一跑就崩，报非法指令。查了半天，代码没问题，问题出在模拟器里的一组 CPU 扩展指令上。给模拟器内核加一个启动参数把它关掉，就好了。这是模拟器环境的事，和 App 无关。

**这个项目是怎么写出来的。**

绝大部分代码是 coding agent 写的。我做的事情主要是看结果，然后说“不对”。

“随机摆的岩点不算还原。”“先别急着求解，先把墙还原对。”“这个小人很假，朝向也有问题。”“示范的人踩到别的颜色，那是踩错了，按规则来。”

回头看，每一句“不对”都在把问题往前推一层：从“看起来像”到“量得准”，从“能算出解”到“解得像人”。写代码已经不是瓶颈了，知道什么才算对，仍然是。
